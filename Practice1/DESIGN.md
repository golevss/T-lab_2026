# Протокол до просмотра тестовых результатов

## Проверяемая гипотеза

При неизменном CatBoost автоматический поиск временных окон и экспоненциального
затухания может улучшить NDCG@10 относительно содержательного ручного набора.
Это исследование ограниченного пространства признаков, а не новый универсальный
метод и не доказательство оптимальности найденного набора.

## Задача

Недельное предсказание просмотров KION среди сэмплированных кандидатов.
Все опубликованные записи 10 000 случайных пользователей, seed=42.
`event_type=watch` — единственный наблюдаемый тип; строки не являются показами.
Все положительные объекты недели, уже встречавшиеся до среза в выбранной когорте,
плюс 99 неотмеченных объектов на запрос: 50 равномерно и 49 с вероятностью,
пропорциональной исторической популярности в степени 0.75. Дубликаты исключены.
`label=0` означает отсутствие записи в этой неделе, а не доказанный отказ.
`label=1` определяется наличием строки, без порога по watched_pct или total_dur;
даже запись с нулевым процентом считается наблюдаемым взаимодействием.
Запрос — пользователь и недельный срез; оцениваем только запросы с хотя бы одним
положительным объектом из доступного каталога. Один объект получает один label,
даже если исходных записей несколько.
Отрицательные кандидаты могут включать ранее просмотренные объекты. При уникальных
парах KION прямая связь поэтому работает как фильтр просмотренного; это свойство
опубликованной таблицы, а не свидетельство моделирования повторного потребления.

Это sampled reranking: будущие положительные объекты принудительно включаются
для офлайн-оценки. Сведения об их метках не передаются в признаки, но сам протокол
не воспроизводит промышленное извлечение кандидатов и завышает абсолютные метрики
по сравнению с ранжированием полного каталога. Никаких заявлений о CTR или
готовности к продакшену на основе этих результатов не делаем.

## Время и допустимая информация

Восемь последовательных недель train, затем неделя validation, затем test.
Для среза t используются только строки с `last_watch_dt < t`; label определяется
на `[t,t+7 дней)`. Окно w: `[t-w,t)`. Все события одной даты считаются
одновременными: внутри даты порядок не выдумываем. Модели validation обучаются
только на train. После фиксации выбора окончательные модели обучаются на train+val,
чьи метки к началу test уже полностью известны.

В истории поздних срезов могут находиться события прошлых срезов: это допустимое
обновление истории во времени. Предсказания внутри недели не обновляются.
Неизвестно, когда менялись метаданные объектов; жанр, тип и возрастной рейтинг
считаем постоянными. Демографию пользователей и динамические метаданные не используем.
`total_dur` не используется; watched_pct применяется только у прошлых строк.
В таблице дата последнего просмотра: более ранние просмотры этой же пары
не восстанавливаются. Сохраняем всю опубликованную историю, а не недоступный сырой лог.
Если пара встречалась и раньше, и позднее, опубликованная последняя дата скрывает
ранние действия. Поэтому это прогнозирование записей опубликованной таблицы:
отсутствие будущих строк в агрегатах проверяется, но полная реконструкция
информации, реально доступной сервису в прошлую дату, не гарантируется.

## Ручной baseline

CatBoostClassifier с LogLoss. Категории: первый жанр, тип контента, возрастной рейтинг.
Агрегаты для user, item, user–item, user–genre, user–content_type: число записей за
всю историю, 7 и 30 дней, давность последней записи (9999 для неизвестной связи).
Доли жанра/типа в истории пользователя: count / (user_count+1).
Тренды item: count_window / (count_all+1).
Сглаженный исторический процент просмотра для user, item и user–genre:
sum(fillna(watched_pct,0)) / (count+1); это не CTR и не несмещённое среднее.
Сырой ID пользователя/объекта не используется как числовой признак.

## Автоматизация

Грамматика фиксирует пять связей выше, автоматически перебирает окна
2, 5, 10, 21, 60 дней и half-life 3, 10, 21 день.
Затухающий агрегат: sum(2 ** (-(t-date)/half_life)).
Пакет окна содержит counts, доли и тренд; пакет half-life содержит пять сумм.
Не больше двух жадных раундов добавления пакетов. В каждом раунде выбирается
лучший validation NDCG@10; добавление требует улучшения > 0.00001.
Скрининг пакетов использует только первую конфигурацию CatBoost.

У baseline и выбранного автоматического набора одинаковая сетка из трёх пар
depth/iterations/learning_rate: (5,180,0.08), (6,260,0.06), (7,320,0.05).
Seed модели 42, l2_leaf_reg=5, CPU threads=6, без early stopping.
Чтобы ограничить вычисления, при обучении используется не более 5000 случайных
полных train-запросов (seed=42), одинаковых для всех вариантов. Истории событий
при этом не обрезаются; для окончательного обучения добавляются все запросы val.
Главный критерий всех выборов — validation NDCG@10, не тест и не ROC-AUC.
Поиск признаков увеличивает бюджет автоматического подхода; это измеряется отдельно.

## Метрики и неопределённость

NDCG@10 с бинарной релевантностью, DCG=sum(label/log2(rank+1)); IDCG — идеальная
сортировка всех положительных кандидатов запроса, ограниченная 10 позициями.
Recall@10 = число положительных в top10 / все положительные кандидаты запроса.
Сначала считаем метрику каждого запроса, затем среднее по запросам, без веса
по числу кандидатов. При равных scores первым идёт меньший item_id.
LogLoss и ROC-AUC считаются по всем строкам, поэтому это другой способ взвешивания.
LogLoss относится к искусственной доле положительных в sampled-наборе; настоящую
вероятность просмотра/клика и калибровку в сервисе он не оценивает.

На test одна неделя, один запрос на пользователя. Для разности NDCG automatic−manual
строим парный percentile bootstrap по пользователям: 2000 выборок с возвращением,
seed=2026, 95% интервал. Он не учитывает неопределённость выбора временного периода,
поиска по validation и сэмплирования пользователей/кандидатов.

## Предопределённые диагностические сравнения

На validation: все сгенерированные признаки; ручной набор без косвенных связей;
ручной набор без прямой связи; только сгенерированные признаки и категории.
Все используют первую конфигурацию CatBoost. Это диагностические сравнения,
а не независимые каузальные эффекты: нет повторного подбора сетки для каждой абляции.
На test дополнительно ранжируем по исторической популярности item за 30 дней.
Вероятностная калибровка для неё не определена, поэтому LogLoss не сообщается.

## Масштабирование

Прозрачная реализация пересчитывает groupby отдельно на каждом срезе.
Если E — число событий, Q — число пар, W — число вариантов, S — число срезов,
приближённая стоимость подготовки O(S·W·(E+Q)), память матрицы O(S·Q·F).
На больших объёмах нужны инкрементальные счётчики/скользящие окна, сортировка
и потоковые as-of joins; экспоненциальные суммы обновляются рекуррентно.
Сэмплирование пользователей снижает качество оценок популярности редких объектов.
Замеры этой работы локальные и не доказывают масштабирование на миллиарды событий.
